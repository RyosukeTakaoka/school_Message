# アーキテクチャ

## 全体像

```
┌──────────────────────────────────────────────┐
│ Features (SwiftUI)                           │
│  RootView / ChatListView / ChatDetailView …  │
│  状態を読むだけ。ロジックを持たない            │
└───────────────┬──────────────────────────────┘
                │ @Observable
┌───────────────▼──────────────────────────────┐
│ ChatStore (@MainActor)                       │
│  画面が読む唯一の状態。取得・送信・既読を統括  │
└──┬──────────┬──────────┬─────────┬───────────┘
   │          │          │         │
┌──▼───┐ ┌────▼─────┐ ┌──▼──────┐ ┌▼──────────┐
│Outbox│ │MediaProc.│ │ Crypto  │ │NetworkMon.│
│actor │ │  actor   │ │  actor  │ │@MainActor │
└──┬───┘ └──────────┘ └────┬────┘ └───────────┘
   │                       │
┌──▼───────────────────────▼───────────────────┐
│ ChatBackend (protocol)                       │
│   ├ CloudKitBackend (actor)  ← 本番          │
│   └ InMemoryChatBackend      ← プレビュー     │
└──────────────────────────────────────────────┘
```

責務の分け方:

- **Core** — モデルと純粋な計算。UI にも通信にも依存しない。
- **Services** — 通信・暗号化・圧縮・永続化。それぞれ actor で隔離する。
- **Features** — 表示と入力のみ。`ChatStore` のメソッドを呼ぶ以外のことはしない。

`ChatStore` を `@MainActor` に置いているのは、参照元がすべて UI であり、
並行アクセスの調停コストを払う価値がないため。時間のかかる処理は
それぞれの actor に逃がしてあるので、メインスレッドは待つだけになる。

## 設計上の判断

以下は「なぜそうしたか」「代わりに何を捨てたか」を残すための記録です。

### 1. メッセージの中身を enum にした

要件で例示された `type` / `text` / `mediaAsset` を並べる形は、
`type == .text` なのに `mediaAsset` が入っている、といった不正な状態を
型の上で作れてしまいます。描画側は毎回 `switch` と `if let` の
二重チェックを強いられ、ケースを増やすたびに抜けが生まれます。

```swift
enum MessageContent {
    case text(String)
    case image(MediaAttachment)
    case video(MediaAttachment)
}
```

- **利点**: 不正な組み合わせを表現できない。View は `switch` ひとつで網羅でき、
  ケース追加時にコンパイラが漏れを検出する。
- **代償**: CloudKit のレコードとの変換に一段変換が必要（`MessagePayload`）。
  ただしこの変換は暗号化のために結局必要なので、実質の追加コストはない。

### 2. 既読はメッセージごとに持たない

`Message.isRead` を実データとして持つと、チャットを開くたびに
未読件数ぶんの書き込みが発生します。7 件未読なら 7 レコード更新で、
CloudKit のレート制限にすぐ当たります。

代わりに **会話 × ユーザで 1 レコード**（`ReadState.lastReadAt`）だけを保存し、
未読数は `sentAt > lastReadAt かつ 送信者 ≠ 自分` の件数として導出します。

- **利点**: 既読化の書き込みが常に 1 回。オフラインでも矛盾しない
  （`lastReadAt` は単調増加させるだけなので、順序が入れ替わっても壊れない）。
- **代償**: 「誰が読んだか」を細かく出す機能（既読者一覧）は別途必要になる。
  MVP の要件には含まれないので今は作らない。
- `Message.isRead` は互換のため残していますが、`lastReadAt` から導出した値です。

自分の送信に付く **「既読」表示** も同じレコードを逆向きに読んで作ります。
相手の `ReadState` の recordName は `readstate-<会話>-<ユーザ>` と決まっているので、
参加者一覧から recordName を組み立てて**一括取得**します（クエリではないので
インデックス設定に依存しません）。1 対 1 なら「既読」、グループなら
`Conversation.readCount(upTo:excluding:)` で人数を数えて「既読 3」と出します。
他人が代わりに書いた既読を信用しないよう、レコードの `userID` と
サーバが押印した作成者が一致するものだけ採用します。

### 2-b. 返信（引用）は暗号化ペイロードに入れる

返信先のメッセージ ID・送信者・本文の抜粋（`ReplyReference`）は、
CloudKit のフィールドではなく `MessagePayload` の中に入れて会話鍵で暗号化します。

- **利点**: 引用文が平文でサーバに残らない。レコードタイプの変更が要らないので、
  Production へのスキーマ再デプロイなしに機能を追加できる。
- **利点**: 抜粋を写して持つので、元メッセージが未読み込みの古い履歴にあっても
  引用の表示自体は壊れない（元へジャンプする操作だけができない）。
- **代償**: 元メッセージを編集・削除しても引用側の写しは変わらない。
  このアプリには編集・削除が無いので問題にならない。

### 3. チャット一覧を会話レコードに非正規化しなかった

最初は `Conversation` に「最終メッセージ」をキャッシュして
一覧を 1 クエリで描く設計を検討しました。しかし CloudKit の
Public Database では **レコードを更新できるのは作成者だけ** です。
グループ作成者以外がメッセージを送っても、会話レコードを更新できません。

全員が書けるようセキュリティロールを緩めると、今度は
第三者が参加者一覧を書き換えられるようになり、メンバー管理の前提が崩れます。

そこで一覧は **Message 側へのまとめクエリ 1 本** で組み立てます
（`conversation IN (自分の会話すべて) AND sentAt > 基準時刻`）。
直近に動きのない会話だけ、個別に最新 1 件を引き直します。

- **利点**: 書き込み権限を緩めずに済む。往復は会話数に比例しない。
- **代償**: 30 日以上動いていない会話の数だけ追加クエリが発生する。
  少人数の学校コミュニティでは実用上の問題にならない。

### 4. 送信は永続キュー（Outbox）を通す

`backend.send()` を画面から直接呼ぶと、以下がすべて破綻します。

- 送信中にアプリが強制終了された → メッセージが消える
- 圏外で送信した → エラーを出すだけで、復帰しても送られない
- 再送ボタンを 2 回押した → 二重投稿

そこで送信は必ず `Outbox`（ディスクに JSON で永続化する actor）に積み、
そこから 1 件ずつ直列に送ります。

- メッセージ ID は**送信前にクライアントが採番**する。CloudKit の
  recordName に使うので、再送しても同じレコードになり重複しない。
  「既に存在する」エラーは成功として扱う。
- 一時的な失敗（圏外・混雑・タイムアウト）は指数バックオフ + ジッタで自動再送。
  恒久的な失敗（容量超過・権限不足）は即座に諦めて再送ボタンを出す。
- 圧縮済みの写真・動画は Application Support に置き、キューが
  「どのファイルがまだ必要か」の唯一の情報源になる。起動時に孤児ファイルを掃除する。
- 直列に送るのは、会話内の順序を保つためと、学校の共有 Wi-Fi で
  複数の動画アップロードを同時に走らせないため。

### 5. プッシュとポーリングを併用する

CloudKit のクエリ購読は、述語の書き方や環境によっては作成に失敗することがあります。
また、ユーザが通知を許可しない場合もあります。

購読の作成に失敗しても致命的な扱いにはせず、
**25 秒間隔のフォールバックポーリング**で新着に気付けるようにしています。
両方の経路は `AsyncStream<BackendEvent>` に正規化されるので、
`ChatStore` はどちらで気付いたかを意識しません。

### 6. 楽観的 UI

送信ボタンを押した瞬間に吹き出しを出し、入力欄を空にします。
アップロードの完了は待ちません。「iPad を開く → 送る」までを短くする、
という UX 目標に直結する部分です。

送信状態は吹き出しの下に「送信中…」→（失敗時のみ）
「送信できませんでした ［再送信］［取り消す］」として出します。
自動再送の途中は「送信中」のままにして、ユーザが何度も再送を押さずに済むようにしています。

## 並行性

- `SWIFT_STRICT_CONCURRENCY = minimal`（Swift 5 言語モード）で始めています。
  CloudKit の型（`CKRecord`, `CKQuery`）が `Sendable` でないため、
  完全な Swift 6 モードには追加の隔離設計が必要です。
  段階的に `targeted` → `complete` へ上げていくのが現実的な順序です。
- actor を跨ぐ値はすべて値型（`Message`, `Conversation`, `OutgoingMessage`）にしてあります。
- `BackendEventHub` だけは `NSLock` を使った `@unchecked Sendable` です。
  `ChatBackend.events()` が同期メソッドとして要求されるためで、
  ロックの範囲は「継続の配列をコピーする」だけに限定しています。
